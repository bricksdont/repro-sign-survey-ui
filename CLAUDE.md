# CLAUDE.md — repro-sign-survey-ui

## What this is

A multi-page metadata annotation tool with two independent tasks: **Reviewing** and **Checking**, plus shared **Datasets** and **Metrics** catalogues. A landing page lets annotators choose which task to work on. Each task has its own overview page listing papers with status badges and a detail page showing the PDF on the left and editable fields on the right. Built for a sign-language NLP survey to track reproducibility metadata (code repos, datasets, metrics) and to verify paper scope.

## Stack

Plain HTML/CSS/JS — no framework, no build step. Node/npm is used only for dev tooling (HTML validation, Playwright tests) — not required to run the app. Don't introduce bundlers or frameworks unless explicitly asked.

## Running

```bash
python3 server.py        # port 8765
python3 server.py 9000   # custom port
# open http://localhost:8765 — redirects to login.html if not authenticated
```

Use `server.py`, not bare `python3 -m http.server`. The custom server adds a `/pdf/<id>.pdf?url=<encoded>` endpoint that fetches PDFs server-side, bypassing both CORS restrictions and `X-Frame-Options: SAMEORIGIN` headers (e.g. OpenReview). Must be served (not `file://`) for the API fetch and proxy to work.

If the direct fetch fails (dead link, paywall), the proxy falls back to fetching `<id>.pdf` from a private Cloudflare R2 bucket, for papers whose PDF has been manually re-hosted there as a preparation step. Requires `boto3` (`pip install -r requirements.txt` — optional for local dev; without it, or without the `R2_*` env vars below set, the fallback is silently skipped and the original fetch error is returned) and four Fly secrets: `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`. No changes to `papers.pdf_url` are needed — the fallback is automatic and keyed purely off the paper's `id`.

"Failure" isn't just a network error or 4xx/5xx status — a `pdf_url` that's a DOI link commonly redirects to a publisher landing page, or gets a WAF/bot-challenge response, both of which can come back as HTTP 200/202 with an empty or HTML body instead of a real PDF. `_looks_like_pdf()` checks the fetched bytes start with the `%PDF-` magic header before accepting a direct fetch as successful; anything else is treated as a failure and falls through to the R2 attempt exactly like a network error would.

## Backend URL

`api.js` checks `window.location.hostname` (the hostname in the browser's address bar) to pick a backend:

| `window.location.hostname` | Backend used |
|---------|-------------|
| `localhost` | `http://localhost:8090` |
| Anything else | `https://repro-sign-survey-backend.fly.dev` |

Override with a URL parameter on any page:

```
http://localhost:8765?backend=remote   # force Fly.io
http://localhost:8765?backend=local    # force local
```

The override is stored in `localStorage` as `pb_backend` the first time it is seen, so it persists across page navigations and logout. It is NOT cleared on logout — it is a routing preference, not a credential.

## Key behaviours

- **Auth**: all pages redirect to `login.html` if no valid PocketBase token is found in `localStorage`. The token is stored with a client-side expiry timestamp (`pb_token_expiry`, `SESSION_TTL_MS` in `api.js`) set to 5 days at login — matching the backend's actual `authToken.duration` on the `users` collection (`432000`s = 5 days, confirmed by querying the live collection config directly), rather than the shorter 24h it used before (issue #88), which discarded still-valid tokens early and forced a relogin on nearly every once-a-day visit. This window is fixed at login time, not sliding/refreshed by activity. `getToken()` in `api.js` returns `null` and clears the keys if the token is missing or expired. Using `localStorage` (not `sessionStorage`) means the token is shared across tabs, so copied paper links open without re-login. Two ways in: email/password (`auth-with-password`) and Slack OAuth2; both end by storing the same `pb_token`/`pb_user_id`/`pb_email`/`pb_token_expiry` keys.
- **Landing page** (`index.html`): five task cards — Reviewing and Review Stats (first row), Datasets and Metrics (second row), Reproducing (Beta) (third row) — plus an account menu. Each card links to its own overview page. All cards are enabled. Checking (`check-index.html`) deliberately has no card here — see below. The "Reproducing" card follows the same gerund-task naming convention as "Reviewing"/"Checking" (its target page is titled the fuller "Reproduction Tracker", same relationship as the "Review Stats" card → its own page); the "(Beta)" suffix flags that this task, unlike the others, is newly launched.
- **Version badge** (issue #21): a small muted `v<version>` link in the bottom-right corner of the landing page, pointing at the matching GitHub release tag. Fetches `package.json` at runtime (served as a plain static file — no build step involved) and reads `.version`; fails silently if unavailable. `package.json`'s `version` field is the single source of truth — bump it with `npm version <patch|minor|major>` when cutting a release, which atomically bumps the field, commits, and creates the matching `vX.Y.Z` git tag, so the badge and the tag can't drift apart. Not currently duplicated onto other pages (each page has its own standalone account-menu markup/JS, so adding it elsewhere means repeating the same small fetch+badge snippet).
- **Breadcrumb navigation**: overview pages show `Home → Reviewing` / `Home → Checking` / `Home → Datasets` / `Home → Metrics` at title-font size; "Home" is a muted grey link, current page is bold black. Detail pages have a `← Back` link returning to the appropriate overview.
- **Reviewing overview** (`review-index.html`): lists all papers from the `papers` collection with ID, title, status badge, and a Review link. Shows counts per status. Search box filters by ID or title (live, substring), with a × clear button (`#search-clear-btn`) that appears once there's text to clear and resets the search on click; same on `check-index.html`. Status filter pills narrow to a specific status. "Review Next →" navigates to a random `needs_review` paper that isn't currently locked by another user (issue #71) — `allPapers` already carries `locked_by`/`locked_at` from the initial fetch, so this needs no extra request; disabled with "No unlocked papers left to review" once every remaining `needs_review` paper is locked.
- **Checking overview** (`check-index.html`): lists all papers from the `check_papers` collection. Status values: `needs_check`, `flagged`, `checked`. "Check Next →" navigates to a random `needs_check` paper that isn't currently locked by another user (issue #71), same as Review Next. **Deliberately internal/unlisted for now**: its landing-page card slot was given to Review Stats (moved up to the first row), which in turn freed the third row for the Reproduction Tracker (previously the unlisted one) to get a card instead — reachable only via a direct link to `check-index.html`, fully functional either way.
- **Two independent collections**: `papers` and `check_papers` are separate PocketBase collections with independent paper sets (a paper may appear in one, both, or neither). The frontend never mixes them.
- **PDF viewer**: native browser `<iframe>` routed through the local proxy (`/pdf/<id>.pdf?url=...`). Text selection, zoom, and all native controls work. No pdf.js. In Checking, the left panel shows the paper's `abstract` (plain text) instead when present — the screening-pipeline batch behind `check_papers` migration 9 ships abstracts but not always a usable `pdf_url`; papers without an `abstract` still fall back to the PDF iframe.
- **Paper navigation**: ◀ ▶ buttons step through papers. URL updates via `history.replaceState` (`?id=<paper-id>`), so every paper has a stable direct link. "Copy link" button in the header copies a plain `?id=<paper-id>` link to clipboard — deliberately built from `papers[currentIndex].id` rather than `window.location.href`, so it never carries the `?q=`/`?status=` nav-filter params described below; a shared/copied link should stay simple and always point at the full collection for whoever opens it.
- **Filtered navigation subset via URL params** (issue #75): `review-index.html`/`check-index.html` keep the active search text and status pill mirrored into their own URL (`?q=<search>&status=<status>`, via `history.replaceState`, params omitted at their default so an unfiltered view keeps a clean URL) — `buildFilterQuery()`/`syncURL()` in `overview.js`/`check-overview.js`. This makes the current view bookmarkable/shareable and is restored on load (`init()` reads `?q=`/`?status=` back into the search box and status pill), so returning via `paper.html`'s Back link lands on the same filtered view; the search box also has a × clear button (`#search-clear-btn`) that appears once there's text to clear. Clicking a row — or the explicit "Review →"/"Check →" link at its end, whose `href` is built with the same `buildFilterQuery()` output rather than left static (issue #91: the row's click handler explicitly ignores clicks on `<a>` elements, so the link's own `href` has to carry the filter itself or a click straight on the link silently drops it) — carries the same `q`/`status` params into `paper.html`'s URL; there, `?id=`/`?q=`/`?status=` are parsed on load and `computeNavOrder()` recomputes the matching subset of paper IDs from the already-loaded `papers` array (same predicate as the overview's `applyFilters()`) — a live recomputation, not a frozen ID list, so it also works for a link shared with someone else or opened in a new tab. ◀ ▶ (`loadAdjacentPaper()`), the `X / Y` counter, and the Back link's `href` (`updateBackLink()`) all stay within this subset; `id`/`q`/`status` are kept in sync in the URL via `history.replaceState` on every paper load (`buildPaperUrl()`). "Copy Link" is the one exception — it always strips `q`/`status` (see above). If the loaded paper isn't in the computed subset (a stale/non-matching `q`/`status`, or Finalize & Next landing outside it — that flow is intentionally left as full-collection, unfiltered, per its existing logic), navigation self-heals by dropping `q`/`status` and falling back to the full collection.
- **Reviewing status workflow** (issue #47): four statuses — `needs_review`, `final`, `flagged`, `rejected`.
  - **Autosave**: every field change (radio, chip add/remove, textarea, N/A toggle, or blurring a pencil-edit field) schedules a debounced save 1 second after the last change (`scheduleAutoSave()`/`runAutoSave()` in `app.js`). Autosave never changes `status` or `finalized_by` — it only persists the editable field values, whatever the current status. A `Saving…` / `Saved ✓` / `Save failed` indicator appears next to the action buttons — `Saved ✓` stays on screen (no auto-hide) once shown, so it doesn't quietly vanish while the reviewer is still working through the form; it's only replaced once another save starts (`Saving…`) or the paper changes (cleared via `hideFooterMessages()` in `loadPaper()`). `persistWithIndicator()` (shared by autosave and Finalize) enforces a 500 ms minimum display time for `Saving…` — against a fast/local backend the PATCH can resolve in a handful of milliseconds, which made the indicator flash too briefly to actually notice the state change once `Saved ✓` was already showing continuously.
  - **Network-failure handling**: `pbGet`/`pbPatch` (`js/api.js`) wrap every request in a 10-second timeout (`fetchWithTimeout()`, via `AbortController`) and catch the network-level failure `fetch()` throws when the backend is unreachable (e.g. stopped) — neither case is an HTTP error status, so `res.ok` alone can't detect them. Without this, an unreachable/hung backend during autosave left the indicator stuck on `Saving…` forever, since the uncaught rejection aborted `runAutoSave()` before it reached the code that would set `Save failed`. `pbPatch` now resolves `{ ok: false, status: 0 }` on either failure — the same shape callers already handle for an HTTP error — so the existing `Save failed — will retry on next change` state is reachable; `pbGet` throws the same kind of `Error` it already throws for an HTTP failure, rather than letting a different, uncaught `TypeError` escape.
  - Pending edits are flushed immediately (not just debounced) before switching papers (◀ ▶, Finalize & Next) and folded into the same keepalive PATCH that releases the edit lock on tab close/navigation (`beforeunload`), so an edit is never silently lost.
  - **Finalize / Finalize & Next** (replacing the old Save / Save & Next) → the only actions that set `status: final` and stamp `finalized_by` with the reviewer's email. Disabled (with a hover tooltip listing what's missing) unless every required field is filled: Title, Year, Peer-Reviewed, Code Repositories (chip or N/A), Datasets (≥1), Metrics (≥1), Area of SLP (≥1), Ranking, Copied Baseline Scores, Human Evaluation, What to Reproduce, Compute Requirements (text or N/A), Textual Conclusion, Ethical Concerns. Also disabled while the paper is `flagged` or `rejected` (tooltip explains to clear/revert first). Finalize & Next then advances to the next `needs_review` paper, skipping flagged/rejected/final.
  - Flag → opens a dialog to choose/enter a reason; stores `status: flagged` + `flag_reason`.
  - Reject → opens a dialog to choose/enter a reason (presets: "not on SLP", "no quantitative experiments", "not published 2017–2026", "not in English", "no full text PDF", "requires specialized hardware" (issue #67), or free text); stores `status: rejected` + `rejection_reason`.
  - Flag and Reject buttons disable each other (clear/revert first).
  - "Clear flag" / "Revert rejection" / "Revert to needs review" link appears next to the badge to reset status, explicitly clearing `flag_reason`/`rejection_reason` to `''` in the same request (issue #63).
  - Rejection/flag reason is folded into the badge text (`⚑ Flagged · <reason>`) and shown as a tooltip.
  - **Attribution**: `finalized_by` (`papers` migration 1, formerly a nonexistent `reviewed_by`) is set only by Finalize / Finalize & Next, to the logged-in reviewer's email; shown next to the status badge (`by <email>`) only once the paper is `final`. Flagging/rejecting does not stamp its own dedicated field — there's no `flagged_by`/`rejected_by` field in the backend — but every transition, flag/reject included, is still attributed via `status_history`'s `by` field (see Status History below), which is what Review Stats' Top Reviewers section reads from.
  - **Status History** (issue #20): a "Status History" button next to "Copy link" opens a dialog listing every status transition, newest first — `<email> changed status from <Before> to <After>` plus a localized timestamp — sourced from `papers.status_history` (`papers` migration 1, a JSON array of `{by, before, after, when}`). Appended to inside `persistPaper()` whenever `extra.status` differs from the paper's current status, so it captures Finalize, Flag, Reject, and Clear/Revert, but never autosave (which never overrides `status`). Empty state: "No status changes recorded yet."
- **Review Stats dashboard** (`stats.html`, issue #54) — named to distinguish it from any future Checking-task stats: loads every record from the `papers` collection (expanded on `datasets`/`metrics`) and computes all breakdowns client-side — no backend aggregation endpoint. Sections: total paper count; status breakdown (needs_review/final/flagged/rejected) as colored bar rows; top reviewers (issue #86 — every status-change entry across every paper's `status_history`, tallied by `by` and summed regardless of transition type, so Finalize/Flag/Reject/Clear-Revert all count — not just `papers.finalized_by`, which only credited Finalize and left flag/reject work, equally real reviewing effort, uncredited; needs no backend changes since `status_history` already records `{by, before, after, when}` for every transition); top datasets (each with an Available/Not available badge sourced from the dataset's own `available` field, via the existing `expand=datasets` on `papers` — `availabilityBadge()` always wraps the badge slot in a fixed-width `.stat-bar-badge-slot`, even when a dataset's availability is unanswered and has no badge to show, leaving the slot empty rather than omitting it; otherwise that row's bar track would start further left than rows that do have a badge. This keeps every row's track left-aligned regardless of badge text width or absence) and top metrics (bars link to the matching `dataset.html`/`metric.html` in a new tab, capped at the top 10 with a "+ N more" note; the label renders in the same accent blue as `.review-link` — at rest, not just on hover — so it reads as clickable, distinct from the plain-text labels in sections like Top Reviewers that don't link anywhere); a breakdown of `area_of_slp` usage (top 12); and a compact table of Yes/No/N-A/Unanswered counts for Peer-Reviewed, Ranking, Copied Baseline Scores, Human Evaluation, and Ethical Concerns. No charting library — bars are plain CSS width percentages, consistent with the "no framework" rule. Reachable from a landing-page card (first row, next to Reviewing); its card description is deliberately short ("Reviewing progress dashboard") compared to the fuller description that used to live there, to keep the first row visually balanced with the plain one-line Reviewing card next to it.
- **Reproduction Tracker** (`reproduction-index.html` + `reproduction.html`, issue #110 — replaces the earlier "Dataset Confirmation Tracker", issue #90, which only tracked whether a paper's datasets were confirmed available; this tracks the actual reproduction *effort*): lists **every** `status === 'final'` paper, same to-do-overview rationale as its predecessor. Backed by a separate `reproductions` PocketBase collection (`repro-sign-survey-backend` PR #62) rather than fields on `papers` — see the dedicated bullet below for why. `js/reproduction/reproduction-overview.js`'s `init()` fetches `pbGetAll('papers', '&expand=datasets,reproductions_via_paper')`, filters to `status === 'final'`, and flattens each paper's reproduction state onto it once: `reproStatus` (`''`/`in_progress`/`finished` — `''` covers both "no reproduction row exists" and a row with an explicitly empty status, since the app treats them identically everywhere), `reproAssignees`, `allDatasetsAvailable`/`allDatasetsOnModal` (`true` only if the paper has ≥1 dataset and every one of them is `available`/`on_modal === 'yes'`). `extractRepro()` normalizes the back-relation expand, which empirically returns a **plain object** for `reproductions_via_paper` (not an array, despite that being PocketBase's general documented shape for back-relations — confirmed against the live backend; `reproductions.paper` is unique, so there's at most one match either way) — defensively handles both shapes in case that ever changes. Same config-driven `FILTERS` array shape as `datasets-overview.js` (`{param, elementId, default, match}`), four entries: Reproduction status (All/Not started/In progress/Finished), Assigned to (All/Only assigned to me/Assigned to anyone/Assigned to nobody — the "anyone"/"nobody" pair added after initial ship, matching on `reproAssignees.length > 0`/`=== 0` rather than a specific email), All datasets available (All/Yes/No), All datasets on Modal (All/Yes/No) — plus the search box (paper ID or title, live substring). Same URL-sync/`.active`-highlight/Clear-filters wiring as `datasets-index.html` (issue #106). Table: truncated Paper ID, Title, Assignees (first email only, same convention as `datasets-overview.js`'s Assignees column, issue #108), Reproduction status badge, All Datasets Available badge, All Datasets On Modal badge, "Details →" (`col-action`). Unlike its predecessor, the table has **no per-paper dataset chips column** — that per-dataset detail moved to the detail page instead (below); showing it here would duplicate the two new aggregate badge columns without adding information at the overview-scanning level. Row click and "Details →" both navigate to `reproduction.html` in the **same tab**, deviating from the old page's new-tab convention — this page is now an active editing workflow (assign yourself, update status), not a static reference list, matching why `datasets-index.html → dataset.html` is also same-tab. Stats row: `"<total> final papers · <notStarted> not started · <inProgress> in progress · <finished> finished"`, same `.stat`/`.stat-sep` markup as `datasets-index.html`. No JSON export (the predecessor's "Download JSON" was dropped, not carried over). Reachable from a landing-page card (third row, full width, titled "Reproducing (Beta)" — see Landing page, above).
- **Reproduction detail page** (`reproduction.html`, issue #110): URL-keyed by the **paper**'s `paper_id` slug (`?paper_id=<paper-id-slug>`), not by the reproduction row's own id or the paper's internal PocketBase id, since a paper may not have a reproduction row yet — rows are created lazily on first save (see below) — and every other cross-link in the frontend (`paper.html`, `review-index.html`, "Used in Papers") already references a paper by `paper_id`, never its internal PocketBase id; using `paper_id` here too avoids leaking that internal id into a public URL. Since PocketBase's REST API only fetches a single record by its own internal id, not by an arbitrary unique field, loading is a filtered list query instead of a direct GET-by-id: `pbGet('/api/collections/papers/records?filter=(paper_id="<slug>")&expand=datasets,reproductions_via_paper&perPage=1')`, taking `items[0]`. That single request loads everything needed: a read-only **Paper** block (`.stats-section`, same bordered-card style as `dataset.html`'s "Used in Papers") showing ID (the paper's `paper_id`), Title, an "Open in Reviewing →" link to `paper.html?id=<paper_id>` (new tab, mirrors the "Used in Papers" cross-workflow-link convention), and a "Datasets" heading with a small read-only table (Name/Available/On Modal — issue #110 follow-up, replacing an initial chip-list design that could only convey one of the two dimensions at a glance via chip color) listing each of the paper's datasets, name linking to `dataset.html?id=<id>` in a new tab, with the same `avail-badge`/`avail-yes`/`avail-no` badge markup `datasets-overview.js` already uses for its own Available/On Modal columns. Below that, an editable form: **Assignees** (verbatim copy of `dataset.html`'s self-assign-only toggle pattern, issue #108 — `toggleAssignMe()`/`renderAssigneeChips()`/`updateAssignMeButton()`, `.text-action-btn` styling), **Reproduction status** (3-way radio, most-progressed state first: Finished `finished` / In progress `in_progress` / Not started `""`), **URLs** (verbatim copy of `dataset.html`'s `urlChips` add/remove pattern), and **Comments** (plain textarea — in the `reproductions` schema but not explicitly named in issue #110; included for consistency with every other collection having one). ◀ ▶ navigation steps through the same filtered subset the paper was opened from (`computeNavOrder()` duplicating `reproduction-overview.js`'s `FILTERS`, same live-recomputation approach as `dataset-detail.js`/`app.js`), with the same `isDirty`-guarded `confirm()` before navigating away with unsaved changes. Save: PATCHes the existing `reproductions` row if one was found via the expand, or POSTs a new one (`{ paper: <paper's internal PocketBase id>, assignees, status, url, comments }` — the relation field always needs the internal id, unlike the URL) if not, then immediately acquires its lock — same two-step create-then-lock sequence as `dataset.html`'s `save()`.
- **`reproductions` collection and independent locking** (`repro-sign-survey-backend` PR #62, issue #110): one row per paper (`paper` relation, required+unique, `cascadeDelete: true`), `assignees` (json array of email strings, same self-assign-only convention as `datasets.assignees`), `status` (select, `in_progress`/`finished` — `""` means "not started," whether because no row exists at all or a row exists with an unanswered status), `url` (json array, unvalidated, same as `datasets.url`), `comments`, and its **own** `locked_by`/`locked_at` — completely independent of the paper's own review lock. This is a deliberate redesign: an earlier version (PR #61, superseded) put `reproduction_*` columns directly on `papers`, but PocketBase access rules are per-*record*, not per-field — the existing review-lock rule (`locked_by = "" || locked_by = @request.auth.id`) gates every write to a paper, so a second lock field on the same record couldn't enable independent editing; whoever held the review lock also blocked reproduction edits, and even acquiring the reproduction lock was itself a write that hit the same wall. A separate collection removes the conflict entirely rather than working around it — verified with two real users in the backend PR: reviewer A's paper lock blocks reviewer B from editing the *paper*, but doesn't block B from creating or editing *that paper's reproduction row*, and vice versa. `reproduction-detail.js`'s `acquireLock()`/`releaseLock()`/`startHeartbeat()`/`isLockExpired()` are an exact copy of `dataset-detail.js`'s (30 min expiry, 60s heartbeat, `beforeunload` keepalive release, failed-PATCH → `setReadOnly(true)`), just pointed at `/api/collections/reproductions/records/<id>` instead. Since `reproductions.deleteRule` is unset (no API delete for a normal user, by design — a reproduction row is meant to persist once work has started), a test or manual mistake that creates a row can't be un-created; the correct fix is resetting every field back to its empty/default value, which the app treats identically to "no row exists" everywhere (`reproStatus`/`reproAssignees` both fall back the same way either way).
- **Checking status workflow**: three statuses — `needs_check`, `flagged`, `checked`.
  - Save / Save & Next → marks as `checked` (only if currently `needs_check`; flagged status is preserved).
  - Save & Next → advances to the next `needs_check` paper; falls back to `check-index.html` if none remain.
  - Flag → opens a dialog to choose/enter a reason; stores `status: flagged` + `flag_reason`.
  - "Clear flag" / "Revert to needs check" link resets to `needs_check`, explicitly clearing `flag_reason` to `''` in the same request (issue #63).
  - **Form validation**: `is_sign_language_processing` must always be answered; `has_empirical_results` is only shown (and required) when `is_sign_language_processing` is `yes`. Both must be answered before Save / Save & Next become active.
  - **Attribution**: every save (`persistPaper()`) writes the logged-in reviewer's email to `checked_by` (`check_papers` migration 10), regardless of status.

Positioned right after URLs, before Available. `datasets-index.html`'s table also gained an **Assignees** column (right after License, before Available) showing only the *first* assignee's email even when there are several — a compact glance, not the full list, which still lives on the detail page's chip list — plus a sixth filter, **Assigned to** (`filter-assigned`, `all`/`mine`), narrowing to datasets whose `assignees` includes the current user's own email; it slots into the same config-driven `FILTERS` array described below (#106), so it gets URL-sync, `.active` highlight, and Clear-filters handling for free.

- **Dataset detail ◀ ▶ navigation** (issue #106): steps through the same filtered/searched subset the dataset was opened from, mirroring `paper.html`'s ◀ ▶ (issue #75) — a `dataset-counter` span ("N / M", or "—" for a new/unsaved record not in any nav order) plus prev/next buttons, disabled at the ends, reusing `paper.html`'s `.paper-nav` CSS directly. `computeNavOrder()` in `dataset-detail.js` duplicates `datasets-overview.js`'s `FILTERS` array/predicates and its own `pbGetAll('papers')` cross-reference for Orphans/Final-paper, so `navOrder` reproduces the exact subset from live data — not a frozen ID list — same approach as `app.js`'s `computeNavOrder()`. **Architectural difference from `paper.html`**: `paper.html` swaps records in-place (one shared in-memory `papers` array, no full page reload, so `beforeunload` never fires for its own ◀ ▶); `dataset.html` keeps its existing one-record-per-page-load model — including its own edit lock acquired/released per load — so ◀ ▶ does a **real navigation** (`window.location.href`) to reuse that lock machinery rather than building a parallel in-place-swap path. That means `beforeunload`'s native prompt wouldn't fire until navigation *already* started, too late to offer a save — so `goToAdjacentDataset()` checks `isDirty` itself first: a plain `confirm()` ("You have unsaved changes. Save them before continuing?") — OK saves (via the existing `save()`) then navigates, only if the save actually succeeds (`isDirty` false afterward); Cancel — or a failed save — keeps the user on the page rather than risking a silent discard. (Labels were originally the fuller "Stored on Modal.com" / "Correspondence with Data Owners" with no tooltip; shortened once a tooltip was added, to declutter the form.) `on_modal` is `yes` / `no` / `""` ("Not answered"), matching `available`'s convention exactly. `correspondence` is `contacted_got_reply` / `contacted_waiting` / `""` — deliberately in that order (most-progressed state first), unlike `available`/`on_modal` which go affirmative → negative → unanswered. Note the empty string means something different here than on `available`/`on_modal`: per the backend PR, PocketBase selects have no per-field defaults, so `""` had to double as "not contacted yet" rather than adding a literal `not_contacted_yet` value (the issue's original spec), to avoid two different values meaning the same thing. The frontend labels that empty-string option "Not contacted" for this field specifically, rather than reusing the "Not answered" wording used elsewhere — the backend PR explicitly flagged that the UI needs to label the shared empty state differently per field. Radio labels themselves are deliberately terse — "Got reply" / "Awaiting reply" / "Not contacted" rather than repeating "Contacted, " on the first two — since that prefix was redundant (both already imply contact was made) and made the row visually crowded. "+ Add Metric" navigates to a blank `metric.html`. The detail page (`metric.html`) has fields for name, URLs (chip list), and comments, with the same edit locking pattern.
- **Unsaved-changes guard** (`dataset.html`/`metric.html`): these pages have no autosave — a Save button persists edits explicitly — so an `isDirty` flag is set by any field mutation (name/license/comments input, availability radio, URL chip add/remove) and cleared on load and after a successful save. `beforeunload` shows the browser's native "leave site?" prompt (`e.preventDefault(); e.returnValue = ''`) whenever `isDirty` is true, covering both actual tab close/reload and in-app navigation (e.g. the Back link), since these pages do a full page load rather than SPA-style routing. Applies equally to a brand-new, not-yet-saved record (`record === null`). While dirty, the lock release + heartbeat-stop that normally runs in `beforeunload` is skipped — releasing the lock immediately would be wrong if the user cancels the prompt and keeps editing — so a lock left behind by a user who dismisses the prompt and leaves anyway just expires via the existing 30-minute inactivity rule instead of being released early. `dataset.html`'s ◀ ▶ navigation (see below) has its own, separate unsaved-changes handling — a `confirm()` checked *before* triggering navigation — since it needs an explicit save step this generic `beforeunload` guard can't offer.
- **Used in Papers** (dataset/metric detail pages only, not for a new/unsaved record): a scrollable, always-fully-shown list of every paper referencing this dataset/metric — title (links to `paper.html?id=<paper-id>` in a new tab) plus a status badge, same class/text mapping as the Reviewing overview table. Computed entirely client-side (`pbGetAll('papers')` filtered by `p.datasets`/`p.metrics` array membership), matching the Review Stats page's approach — no backend relation-filter query involved, so no risk from PocketBase's `~` operator not being an exact array-membership match (confirmed empirically it under-counts for this use case). Loads in the background after the form/lock, doesn't block page interactivity.
- **Persistence**: Save sends a PATCH to the appropriate collection endpoint on PocketBase. Two IDs per record: `paper_id` (kebab slug used in URLs and display) mapped to `p.id`; opaque PocketBase `id` stored as `p._pb_id` and used only for API calls.
- **Pagination**: `pbGetAll(collection)` in `api.js` pages through PocketBase results until all records are loaded, avoiding the 500-record ceiling. Both overview and detail scripts use this helper.
- **Edit locking**: opening a paper acquires a lock by setting `locked_by` + `locked_at` on the record. A heartbeat PATCH fires every 60 s to keep the lock alive. On save, navigation, or tab close the lock is released (`locked_by: ""`). If PATCH returns 404, the paper is locked by another user — the form goes read-only with a notice banner. Lock expiry (30 min of inactivity) is enforced client-side only.
